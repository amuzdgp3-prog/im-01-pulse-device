## 0. Что от тебя нужно

Спроектировать и виртуально проверить устройство учёта импульсов для игровых аппаратов, затем
реализовать серверную часть приёма данных в этом репозитории.

**Начинай с шага 1 плана проверки (§8) — с аналоговой симуляции, не с платы и не с кода.** Порядок
в §8 выбран по принципу «сначала самое дешёвое и самое показательное», не меняй его без причины.

### Чего не делать ни при каких условиях

1. **Не предлагать комбо-модуль** (MCU внутри модема) как экономию. Уже рассматривали и отклонили,
   причина в §2 — она жёсткая, а не вкусовая.
2. **Не писать в `services` и не трогать счётчики игр.** Приём показаний не создаёт обслуживание и
   не участвует в расчёте выручки (§7).
3. **Не отдавать автороутеру три цепи**: трассу до u.FL, коммутирующий узел преобразователя, путь
   VBAT (§8 шаг 5).
4. **Не считать 1000 мкФ на VBAT проверенной величиной** — это отправная точка для симуляции (§5.2).
5. **Не заменять ручные показания** автоматическими. Решение владельца — они идут параллельно.

### Что решать самому, а что спрашивать

- **Сам:** номиналы пассивных элементов, выбор конкретных микросхем внутри заданных классов,
  структура кода и тестов, порядок действий внутри одного шага.
- **Спросить владельца:** оператора и тариф M2M на 500 SIM; подтверждение перед реализацией
  серверного контракта (требование правил репозитория); любое изменение решений из §3.
- **Проверить на пилоте, а не угадывать:** всё из §10.

## 1. Контекст

Репозиторий — система обслуживания игровых аппаратов `2.apixspb.ru` (Node 22 + Fastify +
PostgreSQL 16 + PWA на React/Vite). Сейчас учёт ручной: техник вносит показания механического
счётчика с обязательным фото.

Проектируемое устройство слушает импульсные выходы монетоприёмника и купюроприёмника, накапливает
показания и передаёт их на сервер 2 раза в сутки. Одно устройство на аппарат.
**Партия 500 шт, лимит цены 1709 ₽/шт**, расчётная себестоимость 788–1228 ₽.

Стадия: **проектирование**. Железо, прошивка и серверная часть не реализованы. Контракт API
утверждён владельцем, но не написан.

### Оборудование на аппаратах

| Устройство | Тип | Питание | Интерфейсы | Импульс |
| --- | --- | --- | --- | --- |
| TOP TB74 | купюроприёмник | 12 В | Pulse / RS232 / ccTalk / ID003 | конфигурируется |
| ICT/VNTec VN-5 | монетоприёмник | 12 В, 0.5 А | Pulse / RS-232 | 25/50/100 мс, NO/NC, ≤12 типов монет, 2 монеты/с |
| Coinsolve EU-9 | монетоприёмник | 12 В | Pulse / RS-232 | 25/50/80 мс, NO/NC, INHIBIT, ≤12 типов |

На аппарате один монетоприёмник и один купюроприёмник → **два входных канала**.

## 2. Жёсткое требование владельца

> «Импульсы не должны теряться, иначе финансовая история окажется неверной — это недопустимо.»

Разобраны три механизма потерь:

| Механизм | Природа | Решение | Остаток |
| --- | --- | --- | --- |
| Окно записи в память | Счётчик сохранялся не чаще раза в 60 с ради износа flash | **FRAM**: атомарная запись, без стирания и лимита циклов, сохранение на каждый импульс | ноль |
| Голодание обработчика при передаче | На комбо-модуле счёт и радиостек делят одно ядро; занятость >25 мс теряет фронт | **Отдельный MCU**, линия импульса на вход таймера в режиме внешнего счётчика | ноль |
| Непроверяемость пульс-протокола | Голый фронт на проводе: нет CRC, кадрирования, подтверждения | Фильтр по длительности ≥10 мс, опторазвязка, витая пара, счётчики отбракованных импульсов в батче | мал, но не ноль |

**Почему аппаратный таймер, а не прерывание.** Регистр счётчика таймера инкрементируется схемой
таймера без участия ядра. Даже при полностью заблокированной прошивке (шторм прерываний, занятый
обмен с модемом, ожидание сети) счёт продолжается корректно, ядро читает регистр позже. Это гарантия
схемы, а не обещание программы. На комбо-модуле такой гарантии нет конструктивно — отсюда решение 3
в §3.

**Почему пропадание питания не создаёт окна потери.** Акцептор и устройство сидят на одной линии
12 В, поэтому монета физически не может быть принята, когда у акцептора нет питания — они пропадают
вместе. Ёмкость на входе даёт запас в десятки миллисекунд, чего хватает записать последний импульс.

**Чего гарантировать нельзя — и не надо обещать обратного.** Пульс-протокол непроверяем в принципе.
Полностью верифицируемый счёт даёт только ccTalk/ID003 на TB74, но режимы акцептора
взаимоисключающие: перевод на serial ломает штатный подсчёт самого автомата. Это отдельный и
гораздо больший проект, владельцу озвучено. Остаточная погрешность контролируется сверкой с ручными
показаниями.

## 3. Принятые решения — не пересматривать без владельца

| № | Решение | Обоснование |
| --- | --- | --- |
| 1 | Показания идут **параллельно** ручным, не заменяют их | Решение владельца. Снимает требования к RTC и к абсолютной точности; расхождение двух источников само является сигналом |
| 2 | **Пассивный** отбор сигнала, INHIBIT не подключается | Устройство не управляет акцептором и не встаёт в разрыв штатной проводки — не может нарушить работу аппарата |
| 3 | **Дискретная** схема: отдельный MCU + отдельный модем | Требование §2. Комбо (Air202/LuatOS, MC60/OpenCPU) отклонено |
| 4 | Модем **LTE Cat.1 bis** (Air780E-класс) | Оптом $2.50–12.50 против NB-IoT $5–14, то есть на уровне 2G. Обычное LTE-покрытие, не гасится, полоса достаточна для OTA. 2G отклонён (сеть гасится, модули с OpenCPU сворачиваются); NB-IoT отклонён (дороже всех, развёрнут выборочно, медленный OTA) |
| 5 | Антенна **выводится за пределы** металлического корпуса (u.FL → пигтейл → SMA) | Снимает клетку Фарадея конструктивно. Именно поэтому преимущество NB-IoT (~20 дБ на проникновение) перестало быть аргументом |
| 6 | Только **накопительные счётчики**, без лога отдельных событий | Решение владельца. Лог дал бы ~90 млн строк и +10–15 ГБ в год. Накопительный счётчик вдобавок самовосстанавливается: потерянный батч не теряет деньги |
| 7 | Передача **2 раза в сутки** в заданные часы | Совпадает с расписанием синхронизации iVend (DECISION-032). Часы выставляются на простой аппарата |
| 8 | **Без провижининга** на производстве, идентификация по **ICCID** | Решение владельца. ICCID уже уникален в любой SIM; привязка «устройство → аппарат» ведётся на сервере |
| 9 | **Съёмный** nano-SIM | Оператор не выбран; смена оператора не должна требовать переделки платы |
| 10 | Устройство передаёт **импульсы, а не рубли** | Вес импульса — свойство настройки акцептора, живёт на сервере и штампуется в принятую строку (логика DECISION-001). Неверный вес правится на сервере, а не выездом к 500 аппаратам |
| 11 | RTC и суперконденсатор **исключены** | Следствие решения 6: накопительный снимок не привязан ко времени суток, достаточно серверного `received_at` |

## 4. Спецификация: входной каскад (2 канала)

Устройство висит параллельно входу штатного контроллера, поэтому добавленная нагрузка должна быть
мала относительно возможностей открытого коллектора акцептора (десятки мА).

| Параметр | Значение |
| --- | --- |
| Токоограничивающий резистор на светодиод оптопары | 2.2 кОм → ≈5 мА |
| Оптопара | PC817-класс, CTR ≥ 50 % |
| Обратный диод параллельно светодиоду оптопары | **обязателен** (U_обр PC817 ≈ 6 В) |
| Фильтр на выходе оптопары | 10 кОм + 100 нФ ≈ 1 мс |
| Подтяжка выхода оптопары | на `VDD_EXT` MCU, **не** на VBAT |
| Режим NO/NC | инверсией в прошивке, схема общая |

Обратный диод — не перестраховка: на 500 аппаратах монтажник где-то перепутает провода, и 12 В в
обратном включении убивают светодиод оптопары. Деталь за 1 ₽ против выезда.

## 5. Спецификация: питание

| Параметр | Значение |
| --- | --- |
| Входное напряжение | 9–30 В (покрывает 12 В, 24 В и выбросы) |
| Выход преобразователя | 3.8 В, ≥2 А (MP1584-класс) |
| Ёмкость на VBAT | ≥1000 мкФ low-ESR + 10–22 мкФ керамика у выводов модуля |
| Защита входа | предохранитель + защита от переполюсовки + TVS |
| Средний ток | ≈100 мА |

Широкий входной диапазон выбран намеренно: вопрос «питание с линии акцептора или с отдельного
отвода» решается на монтаже и не блокирует разводку.

### 5.2 Требует проверки симуляцией, не принимать на веру

Цифра **1000 мкФ — инженерная отправная точка, а не проверенное значение**. Ёмкость должна покрывать
только время реакции петли преобразователя (≈10–50 мкс), потому что при частоте коммутации
0.5–1.5 МГц петля успевает отреагировать внутри пачки передачи. Если бы ёмкость должна была нести
всю пачку целиком, требовалось бы `C ≥ I·Δt/ΔV` = 2 А × 577 мкс / 0.2 В ≈ 5800 мкФ.

Что происходит с выбранным преобразователем — считает ngspice (§8 шаг 1). Отдельно учесть: у LTE
Cat.1 нет TDMA-структуры 577 мкс как у GSM, пики мягче, поэтому требование может оказаться слабее.
Скорректировать эту таблицу по результатам симуляции — ожидаемый результат, а не провал.

## 6. Спецификация: диагностика, монтаж, закупка

- **LED1** — мигает на каждый принятый импульс: монтажник бросает монету и видит, что отбор работает.
- **LED2** — статус сети и последней выгрузки.
- **Кнопка** — принудительная выгрузка: весь путь до сервера проверяется на монтаже, а не через 12 ч.
- Втроём ≈8 ₽. На 500 установок — самая выгодная позиция в спецификации.
- **Y-переходник**: штатные провода не резать. С одной стороны разъём в акцептор, с другой гнездо под
  оригинальный жгут, отвод на `impulse`, `GND`, `+12 В`. Разъёмы ключёванные, монтаж обратим.

| Позиция | ₽/шт при 500 |
| --- | --- |
| MCU STM32C0/G0 | 50–80 |
| FRAM | 30–60 |
| Модем LTE Cat.1 bis | 280–450 |
| Оптопары 2 кан. + диоды + RC | 35–45 |
| Преобразователь 2 А + защита + 1000 мкФ | 55–75 |
| Антенна + пигтейл + SMA | 45–65 |
| Держатель nano-SIM + ESD | 20 |
| 2 LED + кнопка | 8 |
| Плата, 2 слоя | 45–65 |
| SMT-сборка turnkey | 110–180 |
| Корпус | 70–110 |
| Y-жгут + разъёмы | 40–70 |
| **Итого** | **788–1228** (лимит 1709) |

Разовые затраты (разработка, прототипы, оснастка) не входят. SIM и тариф — операционные расходы.

## 7. Требования к прошивке

1. **Счёт.** Линия импульса — на вход таймера в режиме внешнего счётчика. Импульс короче **10 мс**
   не засчитывается, а инкрементирует счётчик отбракованных.
2. **Хранение.** Четыре счётчика в FRAM: принятые и отбракованные, по монете и по купюре. Запись на
   каждое изменение. Счётчики не сбрасываются никогда — ни при перезагрузке, ни при потере питания.
3. **Передача.** 2 раза в сутки в заданные часы. Регистрация в сети → `POST` → при HTTP 2xx
   фиксируется подтверждённый `seq`.
4. **Сбой связи.** Несколько повторов с нарастающей паузой, дальше ожидание следующего окна.
   Накопительный характер счётчика означает, что пропуск окна ничего не теряет.
5. **Watchdog.** Перезагрузка при зависании обмена с модемом. Счётчики в FRAM, перезагрузка бесплатна.
6. **OTA.** Обновление прошивки по сотовому каналу входит в объём первой версии: без него ошибка в
   прошивке означает 500 выездов.

## 8. Серверный контракт (утверждён владельцем, не реализован)

`POST /api/pulse/batch`, полезная нагрузка ≈120 байт:

```json
{
  "iccid": "8970101234567890123",
  "seq": 412,
  "coinPulsesTotal": 18340,
  "billPulsesTotal": 2255,
  "coinPulsesRejected": 3,
  "billPulsesRejected": 0
}
```

Три новые таблицы — **зеркала уже работающих и протестированных в этом репозитории**. Копируй их
структуру, а не изобретай свою:

| Новая таблица | С образца | Назначение |
| --- | --- | --- |
| `pulse_devices` | `terminals` | Устройство опознаётся по `iccid` (UNIQUE) |
| `pulse_device_bindings` | `terminal_bindings` | Интервальная история «устройство → аппарат»: `EXCLUDE USING gist` по `tstzrange`, одно активное на аппарат. Перестановка устройства не портит прошлые периоды |
| `pulse_batches` | `cashless_transactions` | Снимки счётчиков; идемпотентность по `(device_id, seq)` через UNIQUE + `ON CONFLICT DO NOTHING`; `forbid_delete`; статус `UNMATCHED` при непривязанном ICCID |

Миграция — новый файл в `api/src/migrations/` с номером больше последнего.

Деньги считаются на сервере: `(coinPulsesTotal − предыдущий) × pulse_value_applied`. Вес импульса
штампуется в строку, поэтому перенастройка акцептора не переписывает деньги за прошлые периоды (та
же логика, что в DECISION-001 после пересмотра).

**Граница данных (критично).** Приём не создаёт `services`, не трогает счётчики игр и не участвует в
расчёте выручки. Это ровно граница DECISION-008, по которой работает импорт безналичных транзакций.
Официальной финансовой историей остаются ручные показания.

**Предупреждение о взаимоблокировках.** `pulse_device_bindings` использует тот же
`EXCLUDE USING gist`, что `terminal_bindings`, и попадает под протокол блокировок DECISION-005 —
порядок взятия advisory-локов надо соблюсти, иначе возможны взаимоблокировки с matcher'ом безнала.

**Аутентификация.** Существующие роуты идут через staff-JWT (`app.authenticate` →
`request.jwtVerify()`), устройство сессию сотрудника держать не может. Решение на время: общий
bearer-токен прошивки, и сервер принимает данные только для ICCID, который админ уже привязал к
аппарату (неизвестный ICCID → `UNMATCHED`, как неизвестный терминал сейчас). Соразмерно потому, что
устройство не пишет в финансовую историю: худший исход при утечке токена — шум в таблице сверки.
После выбора оператора перейти на приватный APN — тогда секрет на устройстве не нужен вообще.

**Тестов на этот слой нет по определению, он новый** — их надо написать (критерии в §9 шаг 2).

## 9. План проверки с критериями приёмки

Инструменты (проверено на Ubuntu 24.04 с root-правами):

```bash
# шаг 1 — аналог
apt-get install -y ngspice && pip3 install PySpice

# шаг 2 — сервер (контейнер не нужен, поднимается локально теми же миграциями)
apt-get install -y postgresql-16
cd api && npm install

# шаг 3 — прошивка
apt-get install -y gcc-arm-none-eabi
# Renode 1.17.0 (07.09.2026), github.com/renode/renode/releases:
#   renode_1.17.0_amd64.deb  либо  renode-1.17.0.linux-portable.tar.gz
pip3 install robotframework

# шаг 5 — плата (в самом noble только KiCad 7.0.11, для 9 нужен PPA)
add-apt-repository -y ppa:kicad/kicad-9.0-releases && apt-get update
apt-get install -y kicad
```

### Шаг 1. ngspice — аналог

Проверить: входной каскад (импульс 25 мс при 12 В даёт чистый логический переход, спайк 0.2 мс — не
даёт; оба режима NO и NC), просадку VBAT при импульсной нагрузке модема, переполюсовку и выброс на
входе.

**Приёмка:** задержка фильтра < 3 мс (много меньше 25 мс); спайк 0.2 мс подавлен ниже логического
порога; VBAT не опускается ниже минимума питания модуля по даташиту ни в одном цикле; ни один
элемент не выходит за предельные режимы. Если 1000 мкФ не хватает — скорректировать §5.

### Шаг 2. Серверная часть

Поднять postgresql-16, прогнать миграции репозитория, реализовать контракт §8.

**Приёмка** — тесты в стиле репозитория (`npx tsx --test --test-concurrency=1 tests/*.test.ts`):

- повторный `POST` с тем же `(iccid, seq)` вставляет строку один раз;
- батч с неизвестным ICCID сохраняется со статусом `UNMATCHED` и не отбрасывается;
- сопоставление идёт по привязке, действовавшей на момент приёма, а не по текущей;
- убывание накопительного счётчика отклоняется (счётчики монотонны);
- `services` и счётчики игр не изменяются ни одним из сценариев.

### Шаг 3. Прошивка в Renode

Инъекция в GPIO: N корректных импульсов (25/50/80/100 мс) + M спайков короче 10 мс.

**Приёмка:** счётчик принятых = ровно N, отбракованных = ровно M. **Тот же тест обязан пройти во
время идущей выгрузки** — это проверка того самого требования §2, из-за которого отказались от комбо.

### Шаг 4. Сквозная проверка

Renode (прошивка) → AT-заглушка на хосте → реальный API → PostgreSQL.

**Приёмка:** число импульсов, поданных в GPIO, совпадает с числом в строке БД; обрыв связи посреди
передачи не теряет и не удваивает показания после восстановления.

### Шаг 5. KiCad

Схема → расстановка → руками развести и зафиксировать (lock) 3 критичные цепи → автороутер на
остальное → полигон земли → DRC → гербера.

Три цепи, которые разводятся **только руками**:

1. трасса до u.FL — контролируемые 50 Ω, короткая и прямая, целый полигон земли под ней;
2. коммутирующий узел buck-преобразователя — критична площадь петли (высокая di/dt);
3. путь VBAT — несёт броски до 2 А, ширина по падению и нагреву.

**Приёмка:** DRC 0 ошибок, 3 критичные цепи разведены вручную, разводка прочитана человеком. Плату
на 500 шт не отправлять в производство без ревью глазами, чем бы она ни была разведена.

Автороутер: Freerouting (нужна java) или KiCadRoutingTools (требует KiCad 9/10; 428 звёзд, 4123
коммита, релизы с бинарниками, но в официальный PCM ещё не принят, и по README нет push-and-shove,
слепых/погребённых переходных и правил по областям платы).

## 10. Что проверяется только пилотом

Пилот — 5–10 устройств на отладочных платах, до заказа серийной платы:

1. Реальная ширина, полярность и настройки переключателей на TB74, VN-5, EU-9 (осциллограф).
   **Здесь же проверяется главное:** запрограммированы ли акцепторы как «1 импульс = один
   фиксированный кредит». При накопительных счётчиках (решение 6) номинал из суммы импульсов не
   восстанавливается. Если номиналы заданы разным числом импульсов — потребуется перепрограммирование
   500 аппаратов.
2. Реальный шум на пульс-линии рядом с соленоидом монетоприёмника.
3. Запас по току на линии 12 В акцептора → откуда брать питание.
4. Уровень сигнала внутри металлического корпуса с вынесенной антенной на нескольких точках.
5. Типы разъёмов акцепторов для Y-жгута.
6. Обновление прошивки по воздуху.
7. Сверка накопленного счётчика с ручными показаниями за период — единственная проверка остаточной
   погрешности пульс-протокола.

## 12. Правила репозитория — обязательны

Читаются в `CLAUDE.md` и `.claude/rules/modularity.md`. Коротко:

- План перед изменением, затрагивающим больше одного модуля, — **и ждать подтверждения владельца**.
- Один слой за раз: типы → миграции → API-роуты → клиент. Не смешивать в одном шаге.
- Отдельный коммит на каждый логически завершённый шаг, а не один большой в конце.
- Смена контракта (API, схема БД, формат данных) — сначала показать, что меняется, и дождаться
  подтверждения.
- Не трогать код, не относящийся к задаче.
- Если изменение может затронуть работающий функционал — назвать это явно.
- Все сообщения пользователю и в коде — по-русски (DECISION-028).
- Перед изменением уже реализованного поведения проверить, нет ли по нему записи `DECISION-NNN`
  в `DECISIONS.md`.

Команды проверки после изменений:

```bash
cd api && npx tsc -p tsconfig.json --noEmit     # типы API
cd web && npx tsc -b                            # типы клиента
cd api && npx tsx --test --test-concurrency=1 tests/*.test.ts
```

### Про git — внимательно

Владелец изменил правило: **пушить в GitHub после каждого логически завершённого шага**
(`git push -u origin <branch>`), отдельного разрешения на пуш спрашивать не нужно.

**В копии `CLAUDE.md` твоего репозитория может лежать старая формулировка** («коммиты только
локально, не пушить без явного указания»). Правило выше новее — владелец изменил его после того, как
эта копия была сделана; правка не попала в remote, потому что у сессии, где она делалась, не было
доступа на запись в GitHub. Приведи `CLAUDE.md` в соответствие с правилом выше отдельным коммитом.
